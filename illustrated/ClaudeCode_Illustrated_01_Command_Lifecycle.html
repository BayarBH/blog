The big picture

On the surface, Claude Code is a terminal CLI. Under the hood, it's a full agentic system — an autonomous agent with tool-calling capabilities, a layered permission model, a persistent memory system, and multi-agent orchestration.

A single user command passes through five phases from input to completion. Burn this diagram into your mental model — it's the anchor for understanding the entire system:

Let's break it down phase by phase.

Phase 1 — Bootstrap

Entry point: main.tsx

Everything starts in main.tsx. This file is the CLI entry point — Commander.js parses the arguments, then initializes the React + Ink terminal renderer.

But Claude Code makes a critical startup performance decision: before any heavy module loads, it fires off four side-effects in parallel.

// main.tsx — fired as side-effects before other imports
startMdmRawRead()
startKeychainPrefetch()
MDM Settings
Reads Mobile Device Management config for enterprise policy enforcement
Keychain Prefetch
Pre-fetches auth credentials from macOS Keychain to avoid blocking later
API Preconnect
Establishes TCP/TLS connection to Anthropic API ahead of time
GrowthBook Init
Initializes the feature-flag system to determine which capabilities are enabled
Design decision: Startup time = max(slowest of four parallel tasks), not their sum. This is why Claude Code's cold start feels faster than you'd expect — by the time you type your first character, auth and connection setup are already done.

Meanwhile, heavy modules are lazily loaded. OpenTelemetry (~400KB) and gRPC (~700KB) are deferred via dynamic import() until actually needed.

Phase 2 — Context Assembly

The system prompt is not a string

Most AI apps have a hardcoded system prompt. Claude Code has a prompt assembly machine.

context.ts composes the final system prompt at runtime from multiple sources. The core architecture is a segmented caching system: a SYSTEM_PROMPT_DYNAMIC_BOUNDARY marker splits the prompt into two halves —

  • Static sections: Cacheable across organizations. Base behavioral rules, tool usage specs. These leverage Anthropic API's prompt caching to avoid redundant computation.
  • Dynamic sections: Per-session content — current project context, user's permission mode, connected MCP servers, persistent memories.

There's a function called DANGEROUS_uncachedSystemPromptSection(). The "DANGEROUS" in the name isn't a joke — it marks volatile sections you explicitly want to break cache. The naming is defensive programming: if you misuse it, the function name makes you think twice.

Design decision: The cache boundary in the system prompt is a direct expression of token economics. Static sections are computed once and cached; dynamic sections recompute every turn. Wrong zone = wasted tokens or stale information.

Phase 3 — Input Routing

Two paths

Path A: Slash commands. Input starting with / hits the commands.ts registry. About 50 commands — /commit, /review, /compact, /doctor. These execute locally without touching the LLM.

Path B: Natural language. Everything else goes to QueryEngine — a single 46,000-line file handling streaming responses, the tool-call loop, thinking mode, retry logic, and token counting.

Path B is where Claude Code becomes an agent. Let's enter the core loop.

Phase 4 — Tool-Call Loop

This is the single most important mechanism in Claude Code. If you remember only one diagram, remember this one:

The loop

The tool-call loop is essentially a while(true). Each iteration:

  • Send current conversation history (system prompt, user message, prior tool calls and results) to the Anthropic API
  • Stream the model's response, parsing each content_block
  • If block type is text, stream directly to terminal
  • If block type is tool_use, run permission check → execute → capture result
  • Append tool_result to messages array; go to step 1

Exit condition: when the response contains only text blocks with no tool_use requests.

The permission system

Every tool_use is intercepted by toolPermission hooks before execution:

Mode Behavior
default Interactive prompts — user approves or denies each tool call
auto ML-classifier-based auto-approval; low-risk operations pass automatically
plan Model plans first, user approves the whole plan
bypass Skip all checks (trusted environments only)

Every action is classified LOW / MEDIUM / HIGH risk. Sensitive files like .gitconfig and .bashrc are guarded. Path-traversal prevention covers URL-encoded traversals, Unicode normalization attacks, and backslash injection.

Design decision: Security is the line between a toy and a product. There's even a "permission explainer" — a separate LLM call generates a human-readable risk description before the user approves.

Phase 5 — Output

Three things at once

Terminal rendering. React + Ink for terminal UI — ~140 components, likely one of the largest public Ink applications.

Cost tracking. cost-tracker.ts records token consumption in real time. Input tokens, output tokens, cache hit ratios. Check via /cost.

Memory consolidation (autoDream). A background "Dream" system with a three-gate trigger: 24-hour gap, 5+ sessions since last dream, concurrency lock acquired. All three must pass. A forked sub-agent then runs four phases: orient → gather signal → consolidate → prune. It gets read-only bash — observation only, no modification.

Recursion: Sub-Agents and Multi-Agent Swarms

When the model calls AgentTool during Phase 4, the entire pipeline gets recursively spawned — own conversation, own tool-call loop, own permission checks.

In advanced mode, coordinator/ transforms a single agent into an orchestrator managing parallel workers. Four stages: parallel investigation → synthesis and spec writing → implementation per spec → verification.

Workers communicate via XML <task-notification> messages with a shared scratchpad for durable knowledge.

Design decision: The core constraint is "no lazy delegation." The coordinator prompt bans "based on your findings" — you must read worker output and specify exactly what to do next. Direct defense against the most common multi-agent failure mode.

Design Decisions and Takeaways

Parallelism-first. Four-way prefetch at startup. Parallel rendering/billing/memory at output. Parallel worker agents. Concurrency at every level.

Caching as first-class citizen. Static/dynamic prompt split, tool schema cache, aggressive feature-flag caching. Tokens are money; every saveable token is saved.

Security isn't bolted on. The permission system is an interceptor chain inside the loop, not a checkpoint outside it. Every tool invocation passes through. No exceptions.

Recursion as extension. AgentTool makes the system fractal. Capabilities scale through recursion, not new modules.
